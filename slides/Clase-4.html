Clases abstractas — el código05 / 31
abstract class Figura {
  constructor(protected color: string) {}

  // CONCRETO: ya está implementado.
  // Todas lo heredan igual.
  describirse(): void {
    const area = this.calcularArea();
    //              ↑ ¡llama a un método que no sabe implementar!
    console.log(`Figura ${this.color} — área: ${area.toFixed(2)}`);
  }

  // ABSTRACTO: sólo la firma.
  // Las subclases ESTÁN OBLIGADAS a implementarlo.
  abstract calcularArea(): number;
}
class Circulo extends Figura {
  constructor(color: string, private radio: number) {
    super(color);
  }
  calcularArea(): number { return Math.PI * this.radio ** 2; }
}

class Rectangulo extends Figura {
  constructor(color: string,
              private ancho: number, private alto: number) {
    super(color);
  }
  calcularArea(): number { return this.ancho * this.alto; }
}
// const f = new Figura("rojo");
// ❌ ERROR: no se puede instanciar una clase abstracta

const figuras: Figura[] = [
  new Circulo("rojo", 5),
  new Rectangulo("azul", 4, 6),
];
figuras.forEach(f => f.describirse());

Al de Circulo.

Aunque describirse() esté escrito en la clase padre, this apunta al objeto real. Si el objeto es un Circulo, this.calcularArea() ejecuta la fórmula del círculo.

Esto es polimorfismo funcionando adentro de la clase padre. Y es una idea muy potente:

La clase padre puede usar métodos que ella misma no sabe cómo se implementan.

Figura define el qué (toda figura se describe mostrando color y área) y delega el cómo a cada hija.

Es lo que hace una receta: “batir los huevos” es un paso fijo, pero cómo los batís —a mano, con batidora— lo decide quien cocina.

¿Por qué Encendible es una interfaz y no una clase de la que Auto y Lampara heredan?

Dame dos razones:
una conceptual y una práctica.

Ver respuestaClick · o tecla R
Razón conceptual

Porque un auto no “es un” encendible.

Probá el test de la frase:

  • “Un Auto es un Encendible” → suena raro. Encendible no es una categoría de cosa: es una capacidad.
  • “Un Auto puede encenderse” → ✔ eso es lo que querés decir.

Un auto es un vehículo. Y además, puede encenderse.

Razón práctica

Si Encendible fuera una clase, Auto no podría extender también de Vehiculo. En TypeScript, Java y C# se hereda de una sola clase. Si gastás esa única herencia acá, te quedás sin la que realmente necesitás.

class Auto extends Vehiculo implements Encendible, Recargable {}  // ✔ válido

La regla: herencia = “es un”. Interfaz = “puede hacer”.

abstract class Animal {
  constructor(protected nombre: string) {}
  abstract hacerSonido(): void;
}

interface Volador { volar(): void; }
interface Nadador { nadar(): void; }

class Pato extends Animal implements Volador, Nadador {
  hacerSonido(): void { console.log(`${this.nombre}: ¡Cuac!`); }
  volar():       void { console.log(`${this.nombre} vuela torpemente`); }
  nadar():       void { console.log(`${this.nombre} nada muy bien`); }
}

Si hubieras puesto volar() en Animal, o hubieras hecho una clase Ave con volar() adentro…

class Pinguino extends Ave {
  volar(): void { throw new Error("no vuelo"); }  // ⚠ mentira

Medios de pago

Creá la interfaz MedioDePago con pagar(monto: number): boolean.

  • Efectivo → siempre puede pagar
  • Tarjeta → tiene un limite. Sólo paga si el monto no lo supera.
  • Cripto → tiene una cotizacion. Convierte el monto a cripto y lo muestra.

Después escribí una función cobrar(medio, monto) que sirva para los tres. ¿Por qué te alcanza con una sola?

Ver respuestaClick · o tecla R
interface MedioDePago {
  pagar(monto: number): boolean;
}

class Efectivo implements MedioDePago {
  pagar(monto: number): boolean {
    console.log(`Pagados $${monto} en efectivo`);
    return true;
  }
}

class Cripto implements MedioDePago {
  constructor(private cotizacion: number) {}
  pagar(monto: number): boolean {
    const cantidad = monto / this.cotizacion;
    console.log(`Pagados ${cantidad.toFixed(6)} BTC`);
    return true;
  }
}
class Tarjeta implements MedioDePago {
  constructor(private limite: number) {}

  pagar(monto: number): boolean {
    if (monto > this.limite) {
      console.log(`Rechazado: supera el límite`);
      return false;
    }
    this.limite -= monto;
    console.log(`Pagados $${monto} con tarjeta`);
    return true;
  }
}

// Una sola función, tres medios. Y mañana, cuatro.
function cobrar(medio: MedioDePago, monto: number): void {
  if (medio.pagar(monto)) console.log("✅ Venta confirmada");
  else                    console.log("❌ Venta rechazada");
}

Fijate qué hace cobrar(): nada. No sabe si es efectivo, tarjeta o cripto. No le importa. Sólo sabe que le pasaron algo que sabe cobrar, y confía en el contrato.

Por qué interfaz y no clase abstracta: ¿qué código podrían compartir los tres? Ninguno. Sus implementaciones no se parecen en nada. Una clase abstracta acá sería una cáscara vacía.

(a) — Una interfaz no puede tener atributos con estado.

Podés declarar la forma de una propiedad, pero no un atributo que guarde datos como los de una clase. Una interfaz es un contrato de comportamiento, no un molde de datos. ¿Necesitás compartir altitudMaxima de verdad? → clase abstracta.

(b) — Una interfaz no puede tener implementación.

volar() no puede traer código adentro. Sólo la firma: volar(): void;. ¿Querés que todos vuelen con el mismo código? Otra vez → clase abstracta.

(c) — No se puede instanciar una clase abstracta.

new Ave("Piolín") es un error. Ave es incompleta a propósito: no sabe hacer sonido.

(d) — Pinguino está vacía, y le faltan dos cosas.

No implementa hacerSonido(), que hereda como abstracto de Ave. Y no implementa volar(), que le exige la interfaz. Ninguna de las dos compila.

Y el error más profundo, que no es de sintaxis

Un pingüino no vuela. class Pinguino ... implements Volador está conceptualmente mal, aunque le escribas el método. Vas a terminar con un volar() que lanza una excepción o no hace nada — y eso es peor que no tenerlo.

No implementes una interfaz que tu clase no puede cumplir de verdad.

Sistema de veterinaria

💡 Pista: recorriendo un Animal[], ¿cómo sabés cuáles implementan Vacunable?

Clases: Animal (abstracta) con nombre, edad, describirse() concreto y hacerSonido() abstracto. Perro (raza → “Guau”), Gato (color → “Miau”), Pajaro (especie → “Pío”).

Interfaces: Vacunable { vacunar(vacuna) } y Adiestrable { entrenar(orden) }. Perro implementa las dos, Gato sólo Vacunable, Pajaro ninguna.

Además: una clase Veterinaria con un registro Animal[], un atenderATodos() que llame a hacerSonido() de cada uno, y un vacunarATodos(vacuna) que sólo vacune a los que se pueden vacunar.

Ver respuestaClick · o tecla R
abstract class Animal {
  constructor(protected nombre: string, protected edad: number) {}
  describirse(): void { console.log(`${this.nombre}, ${this.edad} años`); }
  getNombre(): string { return this.nombre; }
  abstract hacerSonido(): void;
}

interface Vacunable   { vacunar(vacuna: string): void; }
interface Adiestrable { entrenar(orden: string): void; }

class Perro extends Animal implements Vacunable, Adiestrable {
  constructor(n: string, e: number, private raza: string) { super(n, e); }
  hacerSonido(): void { console.log(`${this.nombre}: ¡Guau!`); }
  vacunar(v: string): void { console.log(`${this.nombre} vacunado: ${v}`); }
  entrenar(o: string): void { console.log(`${this.nombre} aprendió: ${o}`); }
}

class Gato extends Animal implements Vacunable { /* ...ídem sin entrenar */ }
class Pajaro extends Animal { /* ...ninguna interfaz */ }
class Veterinaria {
  private registro: Animal[] = [];
  registrar(animal: Animal): void { this.registro.push(animal); }

  atenderATodos(): void {
    // Polimorfismo puro: no pregunto de qué tipo es ninguno
    this.registro.forEach(a => a.hacerSonido());
  }

  vacunarATodos(vacuna: string): void {
    this.registro.forEach(animal => {
      if ("vacunar" in animal) {              // ¿cumple el contrato?
        (animal as unknown as Vacunable).vacunar(vacuna);
      } else {
        console.log(`${animal.getNombre()} no se vacuna`);
      }
    });
  }
}

La parte difícil era vacunarATodos(): el array es de Animal, que no sabe nada de vacunas. Hay que preguntar en tiempo de ejecución si el objeto cumple el contrato.

"vacunar" in animal pregunta si el método existe. instanceof Perro || instanceof Gato pregunta por la clase concreta, y es peor: si mañana agregás Conejo, hay que volver a abrir ese if.

La pregunta incómoda

¿Ese if no te suena? Es el mismo if/else que atacamos toda la clase pasada. Volvió disfrazado.

Y acá tiene salida: si Veterinaria tuviera un Vacunable[] aparte del Animal[], el if desaparece. Probá esa versión.
