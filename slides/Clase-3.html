class Animal {
  protected nombre: string;

  constructor(nombre: string) {
    this.nombre = nombre;
  }

  // Será sobreescrito por las subclases
  hacerSonido(): void {
    console.log(`${this.nombre} hace un sonido genérico`);
  }
}
class Perro extends Animal {
  // Misma firma, otro comportamiento
  // → sobreescritura
  hacerSonido(): void {
    console.log(`${this.nombre} dice: ¡Guau!`);
  }
}

const p = new Perro("Fido");
p.hacerSonido();   // Fido dice: ¡Guau!

La firma que rompe la sobreescritura
class Animal {
  hacerSonido(): void { /* ... */ }
}

// Versión A
class Perro extends Animal {
  hacerSonido(volumen: number): void { }
}

// Versión B
class Perro extends Animal {
  hacerSonido(): void { }
}

¿Cuál de las dos sobreescribe de verdad? ¿Qué pasa con la otra?

Ver respuestaClick · o tecla R

Sobreescribe la B.

La A no sobreescribe: le cambiaste la firma. Para el compilador ya no es “el mismo método redefinido” — es un método distinto que resulta que se llama igual.

Pensalo así: alguien que tiene una variable de tipo Animal va a llamar animal.hacerSonido(), sin parámetros. Si adentro resulta ser un Perro de la versión A, falta el volumen. La promesa está rota.

La regla: para sobreescribir, la firma tiene que ser exactamente la misma. Mismo nombre, mismos parámetros, mismo tipo de retorno.

Si necesitás parámetros distintos, no estás sobreescribiendo. Estás haciendo otra cosa, y probablemente el diseño esté mal.

super.metodo() — extender sin reescribir07 / 31

A veces no querés reemplazar lo que hace el padre. Querés hacer lo del padre, más algo tuyo.

class Perro extends Animal {
  private raza: string;

  constructor(nombre: string, raza: string) {
    super(nombre);        // ← el CONSTRUCTOR del padre
    this.raza = raza;
  }

  describirse(): void {
    super.describirse();     // ← el MÉTODO del padre
    console.log(`Soy de raza ${this.raza}`);
  }
}
const p = new Perro("Rex", "Pastor Alemán");
p.describirse();

// Soy Rex
// Soy de raza Pastor Alemán

Ojo: super(...) en el constructor y super.metodo() en un método son dos cosas distintas.

El primero inicializa al padre. El segundo llama a un método del padre.

class Gerente extends Empleado {
  private bono: number;

  constructor(nombre: string, sueldoBase: number, bono: number) {
    super(nombre, sueldoBase);   // el padre primero
    this.bono = bono;
  }

  calcularSueldo(): number {
    return super.calcularSueldo() + this.bono;
    //     ↑ le pido el cálculo al padre, y le sumo lo mío
  }
}
La idea clave

super.calcularSueldo() te da el sueldo base sin que vos sepas cómo lo calcula.

Si mañana la empresa cambia la fórmula del sueldo base — le suma antigüedad, presentismo, lo que sea — Gerente no se toca. El cambio se hace en un solo lugar.

Si en cambio hubieras escrito return this.sueldoBase + this.bono, acabás de duplicar la fórmula. Y el día que cambie, alguien se va a olvidar de actualizar una de las dos copias.

Ese “alguien” suele ser vos, tres meses después.

Muchas formas

Tratar objetos de distintos tipos de la misma manera.

Y que cada uno responda según su propia implementación.

Fijate en el tipo del array: es Animal[], no Perro[].

No importa qué tipo exacto es cada uno. Vos llamás a hacerSonido() y cada uno responde como sabe.

}

// Fido dice: ¡Guau!

// Jacinta dice: ¡Muuu!

Por qué el polimorfismo importa13 / 31
Sin polimorfismo — se pudre con cada tipo nuevo
function hacerHablar(animal: Animal): void {
  if (animal instanceof Perro) {
    (animal as Perro).ladrar();
  } else if (animal instanceof Gato) {
    (animal as Gato).maullar();
  } else if (animal instanceof Vaca) {
    (animal as Vaca).mugir();
  }
  // ¿Agregás Pato? Tenés que venir a tocar ESTE código.
}
Con polimorfismo — no se toca nunca más
function hacerHablar(animal: Animal): void {
  animal.hacerSonido();   // cada uno responde como sabe
}

// ¿Agregás Pato? Creás la clase y sobreescribís
// hacerSonido(). Nada más.

En la versión mala, cada animal tiene un método con nombre distinto — ladrar, maullar, mugir. Eso es lo que obliga al if.

Unificar el nombre del método es lo que habilita el polimorfismo.

En la versión con polimorfismo, si mañana el negocio agrega Pato, Caballo y Loro…

Cero

Escribís tres clases nuevas, cada una con su hacerSonido(). La función hacerHablar() no se toca. El array no se toca. Nada de lo que ya funcionaba se toca.

En la versión con if/else, en cambio, tenés que abrirla y agregarle tres ramas más. Y cada vez que abrís código que ya funcionaba, tenés la chance de romperlo.

Guardate esta idea. Tiene nombre y lo vamos a ver más adelante: abierto a la extensión, cerrado a la modificación. Es uno de los principios SOLID, y lo acabás de aplicar sin saber cómo se llamaba.

class SMS extends Notificacion {

  }
}

Porque el límite de 140 caracteres es un problema del SMS, no del sistema de notificaciones. notificarATodos() no tiene por qué enterarse de que existe.

Si nombre quedara private, las subclases no podrían acceder a él — y PerroCallejero necesita this.nombre para ladrar. protected significa “yo y mis hijas”.

2 · un solo nombre de método

Con los nombres originales no podés escribir animales.forEach(a => a.hacerSonido()) — cada uno tiene un método distinto y volvés al if/else.

Sin eso, la herencia te ahorra duplicación pero no te da nada más.

¿A cuál calcularArea() llama?

Al de la subclase. Aunque el método esté escrito en Figura, cuando el objeto es un Circulo, this es el círculo, y se ejecuta su fórmula.

Figura escribe el procedimiento completo sin saber calcular ninguna área. El padre define los pasos; las hijas completan el paso que solo ellas saben hacer.

Guardate este mecanismo: más adelante vas a descubrir que tiene nombre propio.

    console.log(`Puertas: ${this.cantidadPuertas}`);
  }
}

class AutoElectrico extends Auto {
  constructor(marca: string, puertas: number, private autonomiaKm: number) {
    super(marca, puertas);
  }

  describirse(): void {
    super.describirse();                        // Auto → y este a Vehiculo
    console.log(`Autonomía: ${this.autonomiaKm} km`);

Una línea, tres impresiones

super.describirse() no es “imprimí la línea del padre”. Es ejecutá el método del padre, completo — y ese método, adentro, hace su propio super. AutoElectrico ni sabe que Vehiculo existe.

Regla: super primero cuando estás agregando. Al final solo si querés envolverlo a propósito. ⚠ No lo confundas con el super() del constructor: ese va obligatoriamente primero.

cantidadPuertas: con private también compila — AutoElectrico nunca lo toca directo, super.describirse() lo imprime por ella.

Si super te alcanza, no abras la visibilidad.
