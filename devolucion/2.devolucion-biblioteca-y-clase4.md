## El patrón: el método que avisa, pero no hace

Mirá estos dos métodos de `Libro`, uno al lado del otro:

```typescript
prestar(): void {
  if (this.estaPrestado)
      console.log(`"${this.titulo}" y esta prestado.`)
}

devolver(): void {
  if (!this.estaPrestado) {
      console.log(`"$(this.titulo) no estaba prestado`)
  }
}
```

Los dos hacen la mitad del trabajo: detectan el caso malo y lo avisan. Pero `prestar()` nunca presta el libro y `devolver()` nunca lo devuelve. Falta la línea que cambia el estado:

```typescript
this.estaPrestado = true;    // en prestar()
this.estaPrestado = false;   // en devolver()
```

Si corrieras el programa, todos los libros quedarían disponibles para siempre y un socio podría pedir el mismo libro quince veces.

Te lo marco como un patrón y no como dos errores sueltos porque es la misma idea las dos veces: un método que valida y avisa está incompleto si no ejecuta la acción que le da nombre. El `if` es el guardia de la puerta; falta lo que pasa cuando el guardia te deja entrar.

¿Cómo lo detectabas sin que yo te lo diga? Probando. `libro.prestar()` y después `console.log(libro.estaDisponible())` te contesta `true`, y ahí saltaba solo. Probar el caso que funciona es tan importante como probar el que falla.

## `Libro.ts`

### a) `prestar()` tiene que devolver `boolean`, no `void`

Esta es la más importante de toda la devolución, y no es un detalle de tipos: es la pieza que hace funcionar el ejercicio.

`Socio` va a necesitar preguntarle al libro *"¿te pudiste prestar, sí o no?"*, porque `estaPrestado` es privado y el socio no puede espiarlo. La única forma de que el libro conteste es devolviendo un `boolean`. Con `void`, el socio no se entera de nada y `pedirPrestado()` no se puede escribir.

Y esto ya te había salido en la entrega anterior, así que no es aprenderlo de cero.

### b) `$(this.titulo)` no interpola

En `devolver()` usaste paréntesis `$( )` en vez de llaves `${ }`. Adentro de un template literal sólo interpola `${ }`; con paréntesis JavaScript lo toma como texto común y por consola sale literal:

```
"$(this.titulo) no estaba prestado
```

Es difícil de ver leyendo, porque el ojo lee "interpolación" igual. Y fijate que dos líneas más arriba, en `prestar()`, lo escribiste bien: sabés cuál es, se te escapó uno solo. (De paso, ahí falta también la comilla de cierre después del título.)

### c) `y esta prestado` → `ya está prestado`

Typo en el mensaje. Lo marco sólo porque estos textos los lee un usuario.

### Cómo queda

```typescript
export default class Libro {
  private titulo: string;
  private autor: string;
  private isbn: string;
  private estaPrestado: boolean = false;

  constructor(titulo: string, autor: string, isbn: string) {
    this.titulo = titulo;
    this.autor = autor;
    this.isbn = isbn;
  }

  // Devuelve TRUE si se pudo prestar, FALSE si ya estaba prestado.
  // Ese boolean es lo que después va a leer el Socio.
  prestar(): boolean {
    if (this.estaPrestado) {
      console.log(`"${this.titulo}" ya está prestado.`);
      return false;
    }
    this.estaPrestado = true;    // ← la línea que faltaba
    return true;
  }

  devolver(): void {
    if (!this.estaPrestado) {
      console.log(`"${this.titulo}" no estaba prestado.`);
      return;
    }
    this.estaPrestado = false;   // ← la línea que faltaba
  }

  estaDisponible(): boolean {
    return !this.estaPrestado;
  }

  getTitulo(): string {
    return this.titulo;
  }
}
```

Una de estilo: en `prestar()` habías puesto el `if` sin llaves. Funciona con una sola línea, pero el día que le agregues una segunda, esa segunda se ejecuta *siempre* y el bug es invisible. Poneles llaves siempre.

## `Socio.ts`

Acá está la parte de la que me escribiste, así que vamos despacio.

### Tres cosas de sintaxis

**1. Falta el import de `Libro`.** Sin él, `librosPrestados: Libro[]` no sabe qué es `Libro`.

```typescript
import Persona from "./Persona";
import Libro from "./Libro";     // ← falta ésta
```

**2. `const` no se usa para atributos de clase.** `const MAXIMO: number = 3;` adentro de la clase no compila. Esta confusión la tiene medio mundo, así que vale separar bien las dos palabras:

| | Dónde va | Para qué |
|---|---|---|
| `const` | Dentro de una función o bloque | Una variable que no se reasigna |
| `readonly` | En un atributo de clase | Una propiedad que no se reasigna |

Adentro de la clase va `private readonly MAXIMO: number = 3;` — `private` porque nadie de afuera necesita verlo, `readonly` porque el máximo no cambia.

**3. `numeroDesocio` vs `numeroDeSocio`.** Declarás el atributo con "s" minúscula y el parámetro con "S" mayúscula. Para TypeScript son dos nombres distintos. Elegí uno y usalo en los dos lados.

### Cómo se usa `MAXIMO`

Me escribiste:

> *puse una constante maxima de 3 porque el socio no puede tener mas de tres libros en su poder. Pero sinceramente me bloquee y no sé como usarla.*

Definiste la constante antes de tener dónde usarla, y una constante sola no hace nada: es un número con nombre. Cobra sentido recién cuando aparece la pregunta que la necesita, y esa pregunta es *"¿cuántos libros tiene este socio ahora mismo?"*.

La respuesta ya la tenés escrita sin darte cuenta: `librosPrestados` es un array, y todo array sabe cuántos elementos tiene.

```typescript
if (this.librosPrestados.length >= this.MAXIMO) {
  // ya llegó al tope
}
```

Eso es todo. `MAXIMO` no es una herramienta especial: es un número contra el cual comparar. El `readonly` sólo le pone el cartel de "esto no se toca".

¿Y por qué guardarlo en una constante en vez de escribir `>= 3` derecho? Porque `>= this.MAXIMO` dice qué significa ese número, y porque si mañana la biblioteca permite 5 tocás una línea sola. Con el `3` suelto tenés que buscarlo por todo el archivo, y el que se te escape queda mal para siempre.

### `pedirPrestado()` — te lo dejo hecho

Vale la pena verlo entero, porque es donde se encuentran `MAXIMO` y el `boolean` de `prestar()`:

```typescript
pedirPrestado(libro: Libro): void {
  // Regla 1: la del socio. La sabe el socio.
  if (this.librosPrestados.length >= this.MAXIMO) {
    console.log(`${this.nombre} ya tiene ${this.MAXIMO} libros`);
    return;
  }

  // Regla 2: la del libro. La sabe el libro.
  if (libro.prestar()) {
    this.librosPrestados.push(libro);
    console.log(`${this.nombre} se llevó "${libro.getTitulo()}"`);
  }
}
```

Mirá la estructura, que es el corazón del ejercicio: hay dos reglas y cada una vive donde vive el dato que necesita. El máximo lo sabe el socio, porque `librosPrestados` es del socio. El estado del libro lo sabe el libro, porque `estaPrestado` es del libro.

El socio no pregunta `if (libro.estaPrestado === false)`. No puede: es privado, y ahí está la gracia. Le pide al libro que se preste, y el libro contesta si pudo. Ese `boolean` es lo que hace posible la línea.

## Las dos preguntas de cierre

Las dos las contestaste bien. Te las repaso para afilar el vocabulario, porque son literalmente el tema de la clase 3.

### Pregunta 1 — ¿Podés hacer que el perro coma distinto sin tocar `Animal`?

> *si se puede hacer que el perro como distinto sin tocar a la clase Animal, con el polimorfismo se sobreescribe el metodo y se cambia la logica de comer.*

La conclusión es correcta y el mecanismo que nombrás también. Lo único que conviene separar son los dos nombres, porque los usaste como si fueran uno:

| | Qué es | Cuándo |
|---|---|---|
| Sobreescritura | La **acción** de redefinir en la hija un método del padre | Cuando escribís el código |
| Polimorfismo | La **consecuencia**: un mismo llamado da respuestas distintas según el objeto | Cuando el programa corre |

Dicho corto: sobreescribís para conseguir polimorfismo. Uno es la causa, el otro el efecto. La respuesta redonda sería *"sí, redefiniendo `comer()` en `Perro` con la misma firma. A eso se lo llama sobreescritura, y `Animal` no se toca."*

### Pregunta 2 — Que cada animal haga su sonido, sin un `if` por tipo

> *hacemos una clase generica llamada Animal y hacemos que todos los animales tengan el mismo método, por ejemplo hacerSonido(), pero que cada clase se comporta de manera diferente.*

También correcta, y el armado está bien descrito. Le falta la parte que contesta la pregunta: por qué eso hace que el `if` no haga falta.

El armado que describís sirve para poder escribir esto:

```typescript
const animales: Animal[] = [new Perro("Fido"), new Gato("Luna"), new Vaca("Aurora")];

animales.forEach(a => a.hacerSonido());
```

El array es de tipo `Animal`, así que podés meter perros, gatos y vacas juntos porque los tres *son* animales. Y ese `a.hacerSonido()` no decide nada: no hay ningún `if`, la decisión de qué versión ejecutar la toma el objeto en el momento de correr.

El detalle que lo vuelve valioso: si mañana agregás `Caballo`, esas tres líneas no se tocan. Con un `if` por tipo tendrías que volver a abrirlas cada vez. El `if` desaparece porque cada objeto ya sabe qué hacer; no hay que preguntarle qué es.

### `Tarjeta.ts` — la lógica está bien, y usaste algo que no habíamos visto

```typescript
constructor(private limite: number) {}
```

Eso se llama **parameter property**: una forma corta de TypeScript para declarar el atributo y asignarlo en un renglón. Equivale a las cuatro líneas que venías escribiendo, y lo usaste bien.

Pero le falta una línea, y es la misma que faltaba en `Libro`:

| | Qué hace | Qué le falta |
|---|---|---|
| `Libro.prestar()` | Detecta si ya estaba prestado y avisa | `this.estaPrestado = true` |
| `Tarjeta.pagar()` | Detecta si supera el límite y contesta | `this.limite -= monto` |

La tarjeta aprueba el pago pero nunca descuenta: con un límite de $3000 podés pagar $3000 quince veces seguidas. No quiero que arregles esta línea, quiero que reconozcas la forma del error. Cada vez que escribas un método que decide algo, preguntate: **¿el objeto quedó distinto después de llamarlo?** Si aprueba una operación y el objeto queda idéntico, falta la línea que cambia el estado.

Y una de estilo. Esto:

```typescript

```

es exactamente esto:

```typescript
return monto <= this.limite;
```

Un `if` que devuelve `true` o `false` es, él mismo, un booleano. (Ojo: con el descuento adentro el `if` vuelve a hacer falta, pero el razonamiento vale igual.)

### `Cripto.ts` — el bloqueo

```typescript

}
// Y la logica no se me ocurre como hacerla
```

Primero lo técnico: ese método no compila. Declaraste que devuelve `boolean` y no devuelve nada. Si alguna vez querés dejar algo a medias sin romper el archivo entero, poné un `return false;` provisorio y un comentario.

Y el bloqueo, que es la misma forma que tuviste con `MAXIMO`: ahí tenías el número y te faltaba contra qué compararlo, acá tenés dos números y te falta qué operación va entre ellos.

- `this.cotizacion` → cuántos **pesos** vale **1 cripto**
- `monto` → cuántos **pesos** querés pagar

```

```

Los pesos se cancelan y queda criptos. La operación es la división, y no hace falta intuirla: las unidades te la dictan.


Justificalo vos: si la cotización fuera de $60.000.000 por bitcoin y quisieras pagar $60.000.000, ¿cuántos bitcoins deberían salir? Probá tu fórmula con ese número. Si da 1, la operación está bien. Ese es el método — elegí un caso donde sepas la respuesta de antemano y verificá que la cuenta la reproduzca.

## Ejercicio 3 — ¿Interfaz o clase abstracta?

Tres de cuatro con la justificación correcta, y el cuarto tiene la conclusión bien: lo que hay que ajustar es el motivo, que en este ejercicio era todo el punto.

| Caso | Elegiste | ¿Correcto? | Tu justificación |
|---|---|---|---|
| 1 — Notificacion | Clase abstracta | Sí | *"tiene atributo y un método igual para todos"* ✔ |
| 2 — Documento / Partida / Nivel | Interfaz | Sí | *"todos los documentos comparten comportamiento"* ⚠️ |
| 3 — Empleado | Clase abstracta | Sí | *"atributos en común y un método que se cumple en cada empleado"* ✔ |
| 4 — Perro / Auto / Reloj | Interfaz | Sí | *"no tienen nada que ver, sólo comparten comportamiento"* ✔ |

En el 1 y el 3 nombraste las dos cosas que piden clase abstracta (estado compartido + método común), y en el 4 escribiste una frase que es prácticamente la definición del criterio.

### Poné tus dos justificaciones de interfaz una al lado de la otra

> **Caso 4:** *"perro, auto y reloj **no tienen nada que ver**, sólo comparten comportamiento"*
>
> **Caso 2:** *"todos los documentos comparten comportamiento"*

Le falta la primera mitad. Y no es un detalle de redacción: *"comparten comportamiento"* no sirve como criterio, porque una clase abstracta también comparte comportamiento. Si eso alcanzara para decidir, las dos opciones darían lo mismo siempre.

| Comparten... | Herramienta |
|---|---|
| Comportamiento **+ atributos + parentesco** ("es un") | Clase abstracta |
| **Sólo** la capacidad, y no se parecen en nada más | Interfaz |

Y hay un segundo detalle: escribiste *"todos los documentos"*, pero el caso no era sobre documentos. Era sobre un documento, una partida de ajedrez y un nivel de videojuego. Si fueran todos documentos —de texto, PDF, firmado— sí podría ser una clase abstracta: son variantes de una misma cosa. Lo que fuerza la interfaz es que del otro lado hay una partida de ajedrez.

La pregunta que resuelve los cuatro casos: ¿estos son variantes de una misma cosa, o cosas distintas que casualmente saben hacer lo mismo? Variantes → abstracta. Cosas distintas → interfaz.

### El nombre de la interfaz

En el archivo `Guardable.ts` escribiste `export default interface Documento { }`. El nombre del archivo estaba bien; el de la interfaz se fue para otro lado.

**La interfaz se llama por la capacidad, no por la cosa que la tiene.** Si se llama `Documento`, la partida de ajedrez tendría que escribir `class Partida implements Documento`, y eso se lee *"una partida de ajedrez es un documento"*. No lo es. Lo que comparten no es una identidad, es una habilidad.

| Qué es | Forma del nombre | Tus ejemplos |
|---|---|---|
| Clase | Sustantivo — una cosa | `Libro`, `Empleado`, `Notificacion`, `Archivo` |
| Interfaz | Adjetivo, casi siempre en `-able` / `-ible` | `Cargable`, `Comparable`, `Vacunable` |
| Método | Verbo — una acción | `prestar()`, `pagar()`, `abrir()` |

Y fijate: `Cargable` y `Comparable` los nombraste vos, y están perfectos. El patrón ya lo tenés; en `Documento` se te escapó uno.

### Dos menores

- `export defualt` en `Notificacion.ts` — está `defualt` en vez de `default`. No compila, pero el editor te lo subraya al toque.
- Separaste `Guardable` y `Cargable` en dos interfaces. La consigna sugería una sola, pero partirlas no está mal: hay una razón buena para hacerlo y tiene nombre propio. Lo vamos a ver más adelante; cuando llegue, acordate de que ya lo habías hecho por instinto.

## Ejercicio 5 — Reproductor multimedia

### `Archivo.ts` — bien

La elección y el motivo son correctos: hay estado compartido (`nombre`, `tamanioMb`) y un método común de verdad (`info()`). Y "una canción **es un** archivo" pasa el test de la frase. Falta escribirle el contenido, pero el criterio está bien.

### `Abrir.ts` — acá hay un concepto que se dio vuelta

```typescript
export default abstract class Abrir {
    //clase abstracta porque todos los objetos comparten un mismo metodo
    // y cada uno lo implementa distinto
}
```

Tu razonamiento es correcto. Lo que está mal es dónde lo aplicaste.

Es cierto que todos los archivos comparten `abrir()` y cada uno lo implementa distinto: eso describe un **método abstracto**. Pero un método abstracto vive adentro de una clase, no es una clase él mismo. Volvé a la tabla de nombres: `Abrir` es un verbo, y los verbos son métodos. `Archivo` es el sustantivo, y ése sí es la clase.

O sea: lo que escribiste como una clase entera era un renglón adentro de `Archivo`.

```typescript
export default abstract class Archivo {
  constructor(protected nombre: string, protected tamanioMb: number) {}

  info(): void {
    console.log(`${this.nombre} (${this.tamanioMb} MB)`);
  }

  abstract abrir(): void;   // ← acá estaba tu clase Abrir
}
```

Hay además un motivo práctico: si `Abrir` fuera una clase, `Cancion` tendría que hacer `extends Archivo` **y** `extends Abrir` a la vez, y TypeScript no permite heredar de dos clases. Se rompería solo.

Para pensar: si `Abrir` no puede ser una clase, ¿podría ser una interfaz? Técnicamente sí. Pero, ¿aportaría algo, si *todos* los archivos abren? Pista: las interfaces sirven cuando la capacidad la tienen algunos y no otros.

| **Cancion** | Sí | Sí | No |
| **Video** | Sí | Sí | Sí |
| **Imagen** | Sí | No | Sí |

Y contestá: ¿qué árbol de herencia produce esa tabla? Probá. Si hacés una clase intermedia `ArchivoReproducible`, `Imagen` se queda sin `exportar()`. Si hacés `ArchivoExportable`, `Cancion` se queda sin `play()`. Ninguna jerarquía la reproduce, porque las capacidades se cruzan: se reparten en diagonal, no en ramas. Ése es el escenario donde la interfaz no es una alternativa a la herencia, es la única salida.

La columna `abrir()` está llena para los tres → eso va en la clase abstracta. Las otras dos tienen agujeros → ésas son las interfaces. La tabla te dicta el diseño.

## Ejercicio 6 — Veterinaria

Lo que hay es esto:

> *"Sinceramente no se me ocurre cómo puede saber cuál Animal del array implementa la interfaz Vacunable."*

Frenaste en el lugar correcto: ésa era la parte difícil, y la consigna la marcaba con una pista.

### La respuesta

El array es `Animal[]`, y `Animal` no sabe nada de vacunas. Necesitás preguntar en tiempo de ejecución si ese objeto cumple el contrato:

```typescript
vacunarATodos(vacuna: string): void {
  this.registro.forEach(animal => {
    if ("vacunar" in animal) {                        // ¿tiene el método?
      (animal as unknown as Vacunable).vacunar(vacuna);
    } else {
      console.log(`${animal.getNombre()} no se vacuna`);
    }
  });
}
```

`"vacunar" in animal` pregunta si ese objeto tiene ese método. No pregunta de qué clase es: pregunta qué sabe hacer. La otra forma sería `if (animal instanceof Perro || animal instanceof Gato)`.

Las dos funcionan hoy. ¿Por qué la primera es mejor? Pensá qué pasa mañana cuando agregues `class Conejo extends Animal implements Vacunable`. Con una, no tocás nada. Con la otra, tenés que volver a abrir el `if` y sumarle un `|| animal instanceof Conejo` — y el día que te olvides, el conejo no se vacuna y nadie se entera.

### Y ahora la parte incómoda

Ese `if` que acabo de escribir… ¿no te suena de algún lado? Es el mismo `if` por tipo que atacamos toda la clase 3, disfrazado de `in` en vez de `instanceof`.

Que TypeScript te ofrezca la herramienta no significa que sea la respuesta correcta. Hay una versión de `Veterinaria` sin ningún `if` de tipo: si además del `Animal[]` guardás un `Vacunable[]` aparte, `vacunarATodos()` se vuelve un `forEach` pelado. Es más código de registro, pero cero preguntas sobre tipos. Probá esa versión y fijate cuál te gusta más — las dos son defendibles, y compararlas vale más que cualquiera de las dos por separado.

### Pero antes de todo eso

El `if` es el último renglón del ejercicio. Antes van `Animal`, `Perro`, `Gato`, `Pajaro`, `Vacunable`, `Adiestrable` y el esqueleto de `Veterinaria`, y todo eso ya lo sabés hacer: es lo mismo que `Empleado` / `Vendedor` / `Repartidor` del repaso, más las interfaces de hoy. Escribí eso primero; cuando llegues al `if` vas a tener el problema mucho más cerca.
