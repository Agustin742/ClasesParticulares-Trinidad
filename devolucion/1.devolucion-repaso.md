Primero lo importante: **los conceptos están.** En varios lados escribiste código que muestra que entendiste bien encapsulamiento y herencia — el `prestar()` del Libro está prácticamente igual a la solución, y los comentarios que dejaste ahí explicando la lógica son exactamente el tipo de razonamiento que buscamos.

Lo que aparece son sobre todo **errores de sintaxis** (cosas que el compilador te habría marcado en rojo apenas abrías el archivo) y **dos o tres ejercicios que quedaron a mitad de camino**. Nada de eso es "no entender": es otra cosa, y se arregla distinto.

## Antes de los ejercicios: dos cosas que se repiten

Estas dos aparecen en varios archivos. Si las cazás, se te caen la mitad de los errores de una.

### 1. `=` no es `===`

En el `Usuario`:

```typescript
if (this.contrasenia = this.contrasenia)   // ⚠️
```

`=` **asigna**. `===` **compara**. Ese `if` no está preguntando nada: le está asignando la contraseña a sí misma y después evaluando el resultado (que da siempre verdadero). Por eso el login iba a aceptar cualquier cosa.

Es un error clásico y silencioso — no rompe, no avisa, simplemente hace otra cosa. Regla mental: **en un `if` nunca va un `=` solo.**

### 2. Si el dato ya es del objeto, el método no lo recibe por parámetro

Esta es la más conceptual de las dos. En el `Termostato` escribiste:

```typescript
subirTemperatura(temperatura: number): number {
```

Pero la temperatura **ya vive adentro del objeto**: es `this.temperatura`. Si además la pedís por parámetro, tenés dos temperaturas distintas dando vueltas y el método termina modificando la de afuera (la copia) en vez del atributo real.

La pregunta para chequear: *¿este dato lo tiene el objeto o se lo tienen que traer de afuera?*

| Método | ¿Recibe parámetro? | Por qué |
|---|---|---|
| `subir()` | No | La temperatura es del termostato |
| `depositar(monto)` | Sí | El monto viene de afuera, el saldo no |
| `login(pass)` | Sí | La contraseña a probar viene de afuera |

## Ejercicio 1 — Usuario con contraseña

**Lo que está bien:** la estructura de la clase, el constructor, `nombre` y `email` públicos, `contrasenia` privada, y `mostrarInfo()` que muestra los dos datos sin filtrar la contraseña. **Eso último era el punto del ejercicio y lo cumpliste.**

**Para revisar:**

**a) El nombre de la clase.** Quedó `Usuruario` (con una "u" de más). Detalle, pero si después la importás desde otro archivo te va a hacer perder diez minutos.

**b) `contrasenia: number`.** Una contraseña es texto: `string`. Con `number` no podrías guardar `"trini2024"`, y además `"0123"` se convertiría en `123`.

**c) El `if` que no compara** — es el punto 1 de arriba.

**d) `loginPass()` no recibe la contraseña a probar.** La consigna pedía `login(pass)`: le paso una contraseña y me contesta si es la correcta. Sin el parámetro, el método no tiene con qué comparar.

**e) Falta el `return false`.** Si el `if` no se cumple, la función termina sin devolver nada → `undefined`. Poniéndole el tipo de retorno `: boolean`, TypeScript te avisa solo.

**Cómo queda:**

```typescript
export default class Usuario {
  public nombre: string;
  public email: string;
  private contrasenia: string;

  constructor(nombre: string, email: string, contrasenia: string) {
    this.nombre = nombre;
    this.email = email;
    this.contrasenia = contrasenia;
  }

  mostrarInfo(): void {
    console.log(`${this.nombre} — ${this.email}`);
  }

  login(pass: string): boolean {
    if (pass === this.contrasenia) {
      console.log("Acceso correcto");
      return true;
    }
    console.log("Contraseña incorrecta");
    return false;
  }
}
```

Fijate que la contraseña **nunca sale** de la clase: no hay `getContrasenia()`. El objeto no te devuelve el dato, te contesta una pregunta sobre el dato.

## Ejercicio 2 — Termostato

Este es el que más se complicó, pero es de esos casos donde el archivo se rompe temprano y después cuesta ver si lo de adentro estaba bien. Y estaba bastante bien.

**Lo que está bien:** `temperatura` privada, el getter, y la idea de que la validación va **adentro** de subir/bajar y no en un setter. El concepto lo tenías.

**Para revisar:**

**a) Las llaves no cierran.** El `if` de `subirTemperatura` nunca se cierra, así que `bajarTemperatura` quedó **declarado adentro** de `subirTemperatura`. Al final del archivo hay tres `}` seguidas tratando de emparejar. Truco: en VS Code, si hacés clic en una llave te resalta su pareja.

**b) El constructor.** Recibe `temeperatura` (con typo) pero no lo usa: adentro asigna `22` fijo. La consigna decía "arranca en 22", así que el parámetro sobra. La forma más limpia es directamente:

```typescript
private temperatura: number = 22;
```

y no poner constructor.

**c) `return temperatura =+1`.** Acá hay dos cosas:
- `=+` no es `+=`. `temperatura =+ 1` se lee como `temperatura = (+1)`, o sea le asigna **1**. `+=` es lo que sumaba.
- Aunque estuviera bien escrito, modificaría el parámetro, no `this.temperatura`. El estado del objeto quedaría igual.

**d) La validación mira el rango equivocado.** `if (temperatura >= 15 && temperatura <= 30)` pregunta si la temperatura **actual** está adentro del rango — pero si estoy en 30, esa condición da verdadero y me deja subir a 31. Lo que hay que preguntar antes de subir es: *¿ya estoy en el máximo?*

```typescript
subir(): void {
  if (this.temperatura >= 30) {
    console.log("No se puede pasar de 30°");
    return;
  }
  this.temperatura++;
}
```

Es un cambio chiquito de lógica pero cambia todo: en vez de *"¿estoy en rango?"* preguntás *"¿este movimiento me saca de rango?"*.

**Cómo queda:**

```typescript
export default class Termostato {
  private temperatura: number = 22;

  private readonly MINIMA: number = 15;
  private readonly MAXIMA: number = 30;

  getTemperatura(): number {
    return this.temperatura;
  }

  subir(): void {
    if (this.temperatura >= this.MAXIMA) {
      console.log(`No se puede pasar de ${this.MAXIMA}°`);
      return;
    }
    this.temperatura++;
  }

  bajar(): void {
    if (this.temperatura <= this.MINIMA) {
      console.log(`No se puede bajar de ${this.MINIMA}°`);
      return;
    }
    this.temperatura--;
  }
}
```

## Ejercicio 4 — Jerarquía de empleados

**`Empleado.ts` está perfecto.** Atributos `protected`, constructor completo, `mostrarDatos()` bien armado. Nada que tocar.

**`Vendedor.ts`:** la lógica está toda bien — el `super()` primero, `zona` privada, el método propio. Dos cosas de forma:

- **Falta el `import`.** Al estar en archivos separados, arriba de todo va `import Empleado from "./Empleado";`. Sin eso, `extends Empleado` no encuentra nada.
- **Falta la llave de cierre de la clase.** La última `}` cierra `visitarCliente()`, pero la clase queda abierta.

**`Repartidor.ts`:**

- Mismo `import` faltante.
- **`private patenteMoto = number;`** — acá se mezclaron dos sintaxis. Con `=` estás **asignando un valor**; para declarar el **tipo** va `:`. Va así:
  ```typescript
  private patenteMoto: string;
  ```
- **`number` no es el tipo correcto para una patente.** `AB123CD` tiene letras, y `000123` perdería los ceros. Regla útil: **si no le vas a hacer cuentas, es `string`.** Aplica igual a DNI, ISBN, teléfono y código postal.
- Convención de nombres: las clases van en PascalCase (`Repartidor`, no `repartidor`) y los métodos en camelCase (`entregar()`, no `Entregar()`). No rompe nada, pero es lo que se espera en el parcial.

### La justificación — esta parte quiero mirarla con calma

Escribiste:

> *"sueldoBase va protected porque en el correr del tiempo puede cambiar y según cada trabajador también cambia"*

La **conclusión es correcta** (va `protected`), pero el motivo mezcla dos cosas distintas:

| | Qué responde |
|---|---|
| **Visibilidad** (`private` / `protected` / `public`) | **QUIÉN** puede tocar el dato |
| **Que el valor cambie** | Nada que ver — cualquier atributo puede cambiar |

Que el sueldo cambie con el tiempo, o que cada empleado tenga uno distinto, es cierto para **todos** los atributos: `nombre` también es distinto en cada empleado, y no por eso decidimos su visibilidad. Un atributo `private` puede cambiar mil veces; simplemente lo cambia la propia clase.

La pregunta que decide la visibilidad es siempre: **¿quién necesita este dato?**
- Solo `Empleado` → `private`
- `Empleado` y sus hijas → `protected`
- Cualquiera desde afuera → `public` (casi nunca)

Y ahí se conecta con la segunda parte:

> *"No cambiaría mi respuesta si Vendedor tuviera que calcular una comisión sobre el sueldo"*

Con la conclusión que elegiste, no cambia — pero **por casualidad**, porque ya habías puesto `protected`. La pregunta apuntaba a otra cosa: si hubieras dicho `private`, ese escenario es **justo el que te obliga a cambiar**. Para calcular la comisión, `Vendedor` tiene que **leer `this.sueldoBase`** — y `private` significa "solo yo, la clase, no mis hijas". No compilaría.

O sea: la comisión no es un detalle del enunciado, es **la prueba** de que `protected` hace falta. Sin ella, `private` alcanzaba.

**Lo que quiero que te lleves:** la visibilidad no se decide de una vez y para siempre. Empezás cerrando (`private`), y abrís a `protected` **cuando aparece alguien concreto que necesita el dato**. Que el compilador te pida permiso, no que vos se lo regales por las dudas.

## Ejercicio 5 — Variables sueltas vs objetos

Este quedó bastante enredado, así que vamos ordenado.

**Para revisar:**

**a) `nombreProducto2` está declarado dos veces** (líneas 5 y 9 — el segundo debería ser `Producto3`). Error real de compilación… **y también el mejor argumento del ejercicio.** Con variables sueltas te pasa esto; con objetos es literalmente imposible, porque cada producto es su propio objeto. Guardátelo para el texto de la conclusión.

**b) El bloque de `const p1 = new Producto()` quedó adentro de la clase.** Las llaves: la clase abre en la línea 13 y recién cierra en la 48, así que las instanciaciones están adentro del cuerpo. Los objetos se crean **afuera**, debajo del cierre de la clase.

**c) `new Producto()` sin argumentos.** Definiste `constructor(nombre, precio, stock)` — muy bien — pero después lo llamás vacío y asignás los campos a mano:

```typescript
const p1 = new Producto();
p1.nombre = "Heladera";
```

Dos problemas de una: TypeScript te va a exigir los tres argumentos, y `p1.nombre` no se puede tocar porque es `private` (bien puesto). **Con el constructor que ya escribiste, todo esto es una línea:**

```typescript
const p1 = new Producto("Heladera", 250000, 15);
```

Y ahí se ve para qué servía el constructor: es imposible olvidarse un dato.

**d) Los tres setters no validan nada.** `setPrecio`, `setStock` y `setNombre` solo asignan → alguien puede poner precio `-500` o stock `-3`. **Ojo que este es exactamente el problema que vos marcaste bien en el ejercicio 3.** Ya lo sabías; se te escapó al escribirlo. Pasa siempre — detectar el error en código ajeno es más fácil que no cometerlo en el propio.

Además, `setStock()` como tal no debería existir: el stock **no se setea**, se mueve con `vender()` y `reponer()`. Es la misma idea que el saldo de la cuenta y que la temperatura del termostato.

**e) Falta el texto comparativo,** que era la mitad del ejercicio. Te dejo la pregunta que lo ordena: **¿qué pasa cuando en vez de 3 productos son 500?** Con variables sueltas serían 1500 variables y 500 funciones `venderProductoN()`. Con objetos, un array y un `forEach`. El salto no es de "feo" a "más feo": es de **"se puede"** a **"no se puede"**, y eso es lo que justifica todo el paradigma.

## Ejercicio 6 — Biblioteca

### `Libro.ts` — muy bien

`prestar()` y `devolver()` están **prácticamente igual a la solución**, y los comentarios que dejaste explicando el razonamiento muestran que entendiste por qué devuelven `boolean`:

> *"si el libro estaba prestado pasa a estar disponible de nuevo, return = true (devolución exitosa) / return = false (si el libro ya estaba disponible no es necesario devolverlo)"*

Eso es exactamente el punto: el libro **contesta si pudo o no**, y quien lo llama decide qué hacer con esa respuesta. Muy bien.

**Detalles menores:**

- **El constructor recibe `estaPrestado` pero lo ignora** (adentro asigna `false` igual). Está bien que arranque en `false` — lo que sobra es el parámetro. Sacalo: nadie debería poder crear un libro que ya nace prestado.
- `isbn: number` → `string`, por lo mismo que la patente (los ISBN llevan guiones y a veces terminan en `X`).
- `titulo`, `autor` e `isbn` quedaron públicos. Poniéndolos `private` + un `getTitulo()`, mantenés la convención de la clase. El `getTitulo()` además lo vas a necesitar para `mostrarPrestamos()`.
- `getestaDisponible()` → la consigna lo llamaba `estaDisponible()`. Y de paso: **cuando el método no devuelve un atributo tal cual sino una respuesta calculada** (acá `!this.prestado`), el prefijo `get` sobra.

### `Persona.ts`

Bien y corto. Un solo cambio: `nombre` y `dni` deberían ser **`protected`**, porque `Socio` los va a necesitar para los mensajes de `mostrarPrestamos()`. Es literalmente el mismo caso que `sueldoBase` del ejercicio 4. Y `dni` → `string`.

### `Socio.ts` — acá quedó incompleto

Está la herencia (bien: `extends`, `super()` primero, y el "un socio **es una** persona" ✔), pero **falta todo el comportamiento**, que era el corazón del ejercicio:

- [ ] `private librosPrestados: Libro[] = []`
- [ ] `pedirPrestado(libro)` → solo si está disponible **y** tiene menos de 3
- [ ] `devolverLibro(libro)`
- [ ] `mostrarPrestamos()`
- [ ] Las pruebas: que pida 4 libros y que intente pedir uno ya prestado

También: `numeroDesocio` debería ser `private` y va `numeroDeSocio` (la "S" en mayúscula).

**No te lo resuelvo entero a propósito** — este vale la pena terminarlo. Pero te doy el arranque, porque la parte difícil es una sola línea:

```typescript
pedirPrestado(libro: Libro): void {
  if (this.librosPrestados.length >= 3) {
    console.log(`${this.nombre} ya tiene 3 libros`);
    return;
  }
  if (libro.prestar()) {          // ← esta línea
    this.librosPrestados.push(libro);
  }
}
```

Mirá bien ese `if (libro.prestar())`. El socio **no pregunta** `if (libro.estaPrestado === false)` — no puede, es privado, y ahí está la gracia. Le **pide al libro que se preste** y el libro contesta si pudo. Quien sabe si un libro está disponible es **el libro**, no el socio.

Y ese `boolean` que devuelve `prestar()` —el que vos ya escribiste bien— es justamente lo que hace posible esa línea. Ya tenías la mitad difícil hecha.

### Y algo para tener presente

Todos los errores de fondo que aparecieron —el setter que no valida, el stock que se va a negativo, el método que recibe lo que ya tiene— son **la misma idea vista desde ángulos distintos**: el objeto tiene que **defenderse solo**, sin confiar en que el de afuera lo use bien.

Los conceptos los tenés. Lo que falta es que el código llegue a compilar para poder demostrarlo. 💪
